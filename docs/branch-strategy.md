# Mind Orbit MVP — 브랜치 전략 / PR 규칙 / 커밋 규칙

---

## 한눈에 보기

| 항목 | 규칙 |
|---|---|
| `main` 머지 | 팀장(지정 1인)만 가능. 저녁 회의 후 검증 완료 시. |
| 핫픽스 | `fix/hotfix-*` → 팀 합의 후 `main` 직접 머지 → `dev` 동기화 |
| 브랜치 수명 | 반나절~1일 지향. 2일 이상은 위험 신호. |
| PR 크기 | 기능 1개 또는 버그 1개. 10분 안에 파악 가능해야 함. |
| 커밋 형식 | `type: 내용` — 의미 없는 메시지 금지 |
| 머지 방식 | Squash Merge 기본 |

---

## 00. 문서 목적

3명의 프론트엔드 개발자가 짧은 기간 동안 바이브 코딩 방식으로 MVP를 완성하기 위한 협업 규칙을 정의한다.

> **팀 핵심 원칙**
> - 빠르게 초안을 만든다
> - 브랜치 충돌을 줄인다
> - 자주 합친다
> - 모바일 UX와 IndexedDB 안정성을 우선한다
> - 구조를 과하게 고정하지 않는다

> **중요 전제**
> - 프로젝트 구조 가이드에 나온 폴더/파일 구성은 예시다.
> - 실제 구현 중에는 더 단순한 구조로 바뀔 수 있다.
> - 협업 기준은 "정해진 파일 경로"가 아니라 **기능 책임과 변경 범위**를 중심으로 잡는다.

## 01. 브랜치 전략

### 기본 브랜치 구조

```
main
  ↑
 dev
  ↑
feature/*, fix/*
```

| 브랜치 | 역할 |
|---|---|
| `main` | 제출/시연 기준. 항상 보여줄 수 있는 상태 유지. |
| `dev` | 팀 통합 브랜치. 일상적인 개발 결과를 모으는 곳. |
| `feature/*` | 기능 개발용 단기 브랜치. |
| `fix/*` | 버그 수정용 단기 브랜치. |

### `dev → main` 머지 규칙

- **`main` 머지 권한은 팀장(또는 지정 1인)만 가능하다.**
- 타이밍은 저녁 회의 후 `dev` 검증 완료 시로 고정한다.
- 임의로 `main`에 직접 푸시하지 않는다.

### 긴급 핫픽스 경로

`main`에서 치명적인 버그 발견 시 아래 경로를 따른다.

```
fix/hotfix-* 브랜치 생성
  → 팀 전체 구두 합의 후 main 직접 머지
  → 이후 dev에도 즉시 동기화
```

> 핫픽스는 반드시 팀 전체가 인지한 상태에서만 진행한다.

## 02. 브랜치 네이밍 규칙

### 기능 개발

```bash
feature/<기능명>

# 예시
feature/dashboard-create-map
feature/dashboard-delete-map
feature/editor-node-crud
feature/editor-pan-zoom
feature/mobile-fab
feature/storage-autosave
```

### 버그 수정

```bash
fix/<버그명>

# 예시
fix/mobile-layout-break
fix/pinch-zoom-jitter
fix/indexeddb-save-fail
fix/hotfix-map-delete-crash  # 긴급 핫픽스
```

### 문서 / 설정

```bash
chore/<작업명>
docs/<문서명>

# 예시
chore/eslint-config
docs/team-rules
```

---

## 03. 브랜치 수명 규칙

- 기능 브랜치는 **반나절~1일 내 머지**를 기본 원칙으로 한다.
- **2일 이상 살아있는 브랜치는 위험 신호**로 간주한다.
- 오래 걸리는 작업은 더 작은 브랜치로 쪼갠다.

```bash
# 좋은 예 — 작게 나눈다
feature/editor-node-crud
feature/editor-selection
feature/editor-pan-zoom

# 나쁜 예 — 에디터 전체를 한 브랜치에
feature/editor-all
```

## 04. 커밋 규칙

### 커밋 메시지 형식

```bash
type: 변경 내용
```

### 커밋 타입

| 타입 | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `style` | CSS/UI 시각적 변경만 (로직 변경 없음) |
| `docs` | 문서 수정 |
| `chore` | 설정, 패키지, 기타 작업 |

> `style`은 CSS/UI 시각적 변경에만 사용한다. 로직이 포함된 경우 `refactor` 또는 `feat`으로 구분한다.

### 커밋 예시

```bash
feat: 대시보드에서 새 마인드맵 생성 기능 추가
feat: 모바일 FAB 버튼 추가
fix: 핀치 줌 중 화면 튐 현상 수정
fix: 새로고침 후 맵 복구 실패 문제 수정
refactor: 노드 선택 로직 분리
style: 에디터 헤더 여백 조정
docs: 브랜치 전략 문서 추가
```

### WIP 커밋

작업 중간 저장이 필요하면 가능하다. 단, **PR 머지 전에 정리한다.**

```bash
# 작업 중
wip: 노드 드래그 초안

# 머지 전 정리
feat: 노드 드래그 이동 기능 추가
fix: 드래그 종료 후 선택 상태 유지 문제 수정
```

### 금지 커밋 메시지

```bash
# 아래는 사용하지 않는다
fix: 수정
feat: 이것저것 작업
wip
final
진짜최종
```

## 05. PR 규칙

### PR 기본 원칙

- PR 하나 = 기능 하나 또는 버그 하나
- 구조 변경과 기능 변경을 크게 섞지 않는다
- 리뷰어가 PR 제목만 보고도 무엇이 바뀌는지 이해할 수 있어야 한다

```bash
# 좋은 PR 예
대시보드에서 새 마인드맵 생성 가능
모바일 FAB 버튼 추가
핀치 줌 제스처 적용
IndexedDB 자동 저장 연결

# 나쁜 PR 예
에디터 전체 구현
UI 수정 + 저장소 구조 변경 + 라우팅 정리
전반적 리팩터링
```

### PR 머지 조건

- 동작 목적이 명확하다
- 최소 동작 확인이 끝났다
- 기존 흐름을 치명적으로 깨지 않는다
- 공용 코드 변경 시 팀 공유가 되어 있다

### PR 템플릿

```md
## 뭘 했나
- 

## 확인한 것
- [ ] 로컬 실행 확인
- [ ] 모바일 동작 확인
- [ ] 저장/복구 영향 없음
```

## 06. 리뷰 규칙

### 리뷰 우선순위

1. 동작이 맞는가
2. 모바일 UX를 해치지 않는가
3. 데이터 유실 위험이 없는가
4. 공용 로직을 불필요하게 복잡하게 만들지 않았는가
5. 나중에 수정 가능할 정도로만 읽히는가

### 꼭 잡아야 하는 것

- 앱이 깨지는 경우
- 저장/복구가 불안정한 경우
- 모바일 조작이 안 되는 경우
- 공용 상태를 위험하게 바꾸는 경우
- 불필요하게 구조를 크게 흔드는 경우

### 이번 스프린트에서 양보 가능한 것

- 다소 아쉬운 추상화
- 약간의 중복
- 완벽하지 않은 네이밍
- 미래 확장성만을 위한 과한 설계

---

## 07. 머지 방식

기본적으로 **Squash Merge**를 사용한다.

- 작업 브랜치에서는 자유롭게 자주 커밋한다
- `dev`로 머지할 때는 PR 단위로 정리된 커밋 하나로 합친다
- `dev` 히스토리가 기능 단위로 깔끔하게 유지된다

---

## 08. 일일 운영 방식

### 아침 회의 전

- `dev` 최신 상태 pull
- 오늘 작업 브랜치 생성
- 누가 어떤 영역을 담당하는지 공유

### 작업 중

- 큰 기능은 작게 나눠 자주 커밋
- 막히면 오래 끌지 말고 팀에 공유
- 공용 로직 수정 시 먼저 팀에 알림

### 저녁 회의 전

- 머지 가능한 작업은 PR 생성
- 덜 끝났더라도 초안 단위로 공유
- 충돌 가능성이 있는 변경은 저녁 회의에서 조율

---

## 09. 공용 변경 위험 구역

아래 성격의 코드는 충돌 위험이 높다. 변경 전 반드시 팀에 먼저 공유한다.

- 데이터 타입 정의
- 노드/트리 조작 핵심 로직
- 에디터 전역 상태
- 캔버스 좌표/줌/패닝 계산
- 저장소 접근 로직
- 라우팅 진입점

> 공용 코드 변경 시 — 큰 변경 전 팀에 먼저 공유하고, 관련 작업 중인 사람이 있으면 조율 후 진행한다.

---

## 10. 제출 직전 운영 규칙

제출 전에는 기능 추가보다 안정화에 집중한다.

### 확인 우선순위

1. 모바일 화면 깨짐 확인
2. 핀치 줌 / 드래그 / 노드 추가 동작 확인
3. 자동 저장 / 새로고침 복구 확인
4. 맵 생성/삭제 흐름 확인
5. 제출용 빌드/배포 확인

### 브랜치 운영

- 새 기능은 가급적 마지막 날에 `dev`에 넣지 않는다
- 마지막에는 `fix/*` 위주로만 운영한다
- 최종 확인 후 팀장이 `dev → main` 반영

---

## 11. 금지 사항

- 오래 살아있는 대형 브랜치 운영
- 한 PR에 너무 많은 목적 넣기
- 공용 핵심 로직을 공유 없이 크게 수정하기
- 모바일 확인 없이 UI 변경 머지하기
- IndexedDB 관련 변경을 확인 없이 머지하기
- 팀 합의 없이 `main`에 직접 푸시하기
